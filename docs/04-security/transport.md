# Transport Security (v0.2.0-alpha.2)

**Audit reference**: C-1 (2026-10-10 senior technical audit). The studio
previously served plain HTTP on `127.0.0.1:7777` with no transport
encryption. The new contract is **HTTPS by default** with a self-signed
cert generated on first boot.

**S2 correction (2026-10-16)**: the contract above was only true for
`studio start`. The `studio-app` distribution generated the keystore, logged
`https://…`, and then booted a plaintext connector, while its launcher JVM
args pinned the legacy port `7777`. Both entry points now install the
connector through one helper (`TlsConfig.configureListener`), the
canonical defaults live in code, and a permanent app-side handshake test
fails if the default listener ever stops speaking TLS.

## Defaults

| Surface | Scheme | Port | Notes |
|---------|--------|------|-------|
| Studio backend (loopback) | `https` | `7778` | Self-signed cert at `<dataDir>/keystore.jks` |
| Studio backend (opt-out) | `http` | `7777` | Set `--insecure-http` on `studio start`, or pass `--insecure-http` / `-Dpipelinek.studio.runtime.insecureHttp=true` to the app |
| CLI client | `https` | `7778` | Trusts the loopback self-signed cert (operator's local machine) |
| App data dir | — | — | `${user.home}/.pipelinek-studio/runtime` (`studio start` uses `${user.home}/.pipelinek-studio`) |

Explicit overrides always win and never change the scheme on their own:
`-Dpipelinek.studio.runtime.host`, `-Dpipelinek.studio.runtime.port`,
`-Dpipelinek.studio.runtime.dataDir` (the app), or `--host/--port/--data-dir`
(`studio start`). Only the explicit insecure opt-in moves the wire to plain
HTTP, and only then is the legacy port used as the default.

## How the cert is generated

The connector helper `dev.pipelinek.studio.http.TlsConfig.configureListener`
runs in both entry points on every boot and calls
`TlsConfig.loadOrCreateKeyStore(dataDir)`:

1. If `<dataDir>/keystore.jks` exists, load it.
2. Otherwise generate a fresh self-signed cert via Ktor's
   `io.ktor.network.tls.certificates.buildKeyStore` with SAN entries
   for `127.0.0.1` (iPAddress + DNS) and `localhost`, a **2048-bit RSA**
   key, a **SHA-256** signature and **825 days** validity. Ktor's defaults
   (1024-bit, SHA-1, 3 days) are rejected outright by OpenSSL 3 clients
   (`EE certificate key too weak`) and would expire a persisted install
   after a few days.
3. Persist the keystore to `<dataDir>/keystore.jks` with permissions
   `OWNER_READ | OWNER_WRITE` on POSIX. The password is
   `studio-loopback-change-me` — change it in a future S5 hardening
   pass via env var.

The cert is reused on subsequent boots so the operator's
`curl --cacert` / trust-on-first-use decision remains valid.

Keystores generated by builds before the 2048-bit/SHA-256 change still hold
the old 1024-bit, SHA-1, 3-day cert. Delete `<dataDir>/keystore.jks` to
regenerate it; nothing else needs migrating.

With `--insecure-http` no keystore is written: nothing in that mode
serves TLS, so generating a cert would only invite a false trust decision.

## How to opt out

For local development without TLS:

```bash
studio start --insecure-http
```

The CLI's HTTPS client (`StudioHttpClient`) installs a
`trustAll` `X509TrustManager` because the cert is self-signed.
A real deployment must replace this with a truststore pinned to the
studio's CA-issued cert.

## Host / authority allow-list (AAT-SEC-005)

Every request is refused with `400` unless its **transport authority** names a
host in the allow-list (`DEFAULT_ALLOWED_HOSTS` plus `STUDIO_HOST_ALLOWLIST`):

| Wire fact | Used for | Missing / hostile |
|---|---|---|
| `Host` header | HTTP/1.x, and the regular-header form HTTP/2 permits | missing → `400 HOST_HEADER_MISSING`; not allowed → `400 HOST_NOT_ALLOWED` |
| `:authority` pseudo-header | HTTP/2 only | not allowed → `400 HOST_NOT_ALLOWED` |
| both present but different | — | `400 HOST_AUTHORITY_CONFLICT` (RFC 7540 forbids it; treating it as a choice would be smuggling) |

Why the HTTP/2 row exists (2026-10-16, independent verifier blocker B1): real
curl negotiates HTTP/2 against the TLS listener, and Ktor builds
`request.headers` from the HTTP/2 header frame by **skipping every
pseudo-header**, `:authority` included. Reading only `Host` therefore rejected
the canonical listener with `400 HOST_HEADER_MISSING`, and the from-distribution
UAT could never reach `/health` — let alone the runtime. The guard now reads
`:authority` for HTTP/2 requests and still requires `Host` for HTTP/1.1, so a
missing `Host` keeps failing closed on every engine and is never satisfied by
the listen address, the socket peer, or a forwarding header.

`Forwarded` and `X-Forwarded-Host` are **never** consulted: they are client
controlled. A reverse proxy in front of the studio must rewrite `Host` /
`:authority` itself and be added to `STUDIO_HOST_ALLOWLIST`.

Ktor 3.0.1 keeps `:authority` on an `internal` request subclass, so the guard
bridges to it reflectively and optionally: if an upgrade renames that type, the
listener logs one warning and HTTP/2 requests fail closed with
`HOST_HEADER_MISSING` instead of being admitted on an unverified authority. The
real-Netty HTTP/2 regression test (`studio-http` `HostAllowListTest`) pins the
seam, so such an upgrade turns a test red rather than the product silent.

## Why HTTPS even for loopback

The studio carries state that an on-host attacker could read or
forge over plain HTTP:

- the **Idempotency-Key** header (operator identity, replay state);
- the **X-Studio-Lease** header that gates destructive admin ops
  (AAT-SEC-010);
- the **source bytes** the runner writes to disk, which may include
  secrets in code.

Loopback is still loopback — the attacker needs to be on the same
machine — but the on-host threat model includes any process running
as another user, browser extensions, and accidentally-bound interfaces
(`0.0.0.0` instead of `127.0.0.1`). TLS closes these.

## Verifying the wire

Two permanent tests perform a real handshake against the generated cert —
none of them disables certificate verification:

- `studio-cli` `TlsHandshakeR02BTest` — `studio start` serves
  `/api/version` over TLS, and `--insecure-http` serves plain HTTP while
  refusing TLS on the same port.
- `studio-app` `TlsHandshakeR02BTest` — the app entry point, booted as a
  child JVM with no opt-out and no data-dir override, serves
  `/api/version` over TLS. Its client trust anchor is exactly the
  `keystore.jks` that boot produced (with endpoint identification on), so a
  plaintext listener, a different cert, a weak/expired cert, or an unexpanded
  `${user.home}` data dir all fail the test.
- `studio-app` `TlsHandshakeR02BTest` (`canonical from-distribution UAT …`) —
  exports the cert with the documented `keytool` command (executed, exit code
  asserted), drives real curl over HTTP/2 and HTTP/1.1, and runs the canonical
  `scripts/uat-from-distribution.sh` against the booted app. Without a
  PipelineK SDK it must end `UAT_VERDICT: BLOCKED` (exit 3) on the real
  `409 RUNTIME_UNAVAILABLE` and must never print `ALL UAT STEPS PASSED`: the
  test proves the wire reaches the runtime, not end-to-end execution.

## Known limits

- Self-signed cert → browsers will warn. CLI is the primary client
  and trusts the cert by design.
- No ACME / Let's Encrypt automation. A future S5 hardening pass
  can add a proper cert flow.
- The keystore password is a documented constant for loopback use; it is
  not a secret and must not be treated as one.
